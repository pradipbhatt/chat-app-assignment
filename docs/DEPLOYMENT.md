# Deployment

The two halves deploy separately, because a WebSocket server cannot live on a
static host.

| Part | Host | Why |
|---|---|---|
| `client/` | Vercel | static build, global CDN |
| `server/` | Render | long-lived Node process holding WebSocket connections |

They reference each other by URL, so the order below matters.

---

## Before anything: MongoDB Atlas

Render's outbound IP addresses are not fixed on the free plan, so Atlas must
accept connections from anywhere.

1. Atlas → **Network Access** → Add IP Address → **Allow access from anywhere**
   (`0.0.0.0/0`)
2. Atlas → **Database Access** → create a user scoped to the `chatapp`
   database, and use that connection string in production rather than a user
   that can reach your other databases

Without step 1 the server starts, fails to connect, and exits.

---

## 1. Backend on Render

The repository contains `render.yaml`, so Render can read the whole service
definition rather than being configured by hand.

1. Render → **New** → **Blueprint**
2. Connect the GitHub repository and pick the `main` branch
3. Render reads `render.yaml` and proposes the `chat-room-server` service
4. Fill in the values marked `sync: false`, which are deliberately not in the
   repository:

| Variable | Value |
|---|---|
| `MONGODB_URI` | the Atlas connection string, ending in `/chatapp` |
| `ADMIN_USERNAME` | your administrator account name |
| `ADMIN_PASSWORD` | a strong password — this seeds the account on every boot |
| `CLIENT_URL` | leave as a placeholder for now; set it in step 3 |

`JWT_SECRET` is generated by Render. Do not paste your local one.

5. Deploy, then confirm:

```bash
curl https://<your-service>.onrender.com/health
```

It should report `"database":"connected"` and `"auth":"configured"`.

**The free plan sleeps after 15 minutes of inactivity** and takes 30–60 seconds
to wake. For a recorded demo, open the health URL first so the service is warm
before you start.

---

## 2. Frontend on Vercel

From the repository root:

```bash
cd client
vercel --prod
```

Set the one variable the build needs, using the Render URL from step 1:

```bash
vercel env add VITE_SERVER_URL production
```

Then redeploy so the build picks it up. Anything prefixed `VITE_` is compiled
into the public bundle and readable by anyone — never put a secret there.

---

## 3. Point the backend at the frontend

Back in Render, set `CLIENT_URL` to the Vercel URL, with **no trailing slash**:

```
CLIENT_URL=https://your-app.vercel.app
```

It accepts a comma-separated list, so you can keep local development working:

```
CLIENT_URL=https://your-app.vercel.app,http://localhost:5173
```

Render restarts on save. Until this is right, the browser connects to nothing
and the console shows a CORS failure on the Socket.IO handshake — the REST
routes will look fine, which makes this the easiest step to misdiagnose.

---

## Checking it worked

1. Open the Vercel URL in two browser windows
2. Join the same room with different names
3. Send a message each way — both should appear instantly
4. Check the connection badge reads **Connected**, not Offline

If messages do not move but the page loads, it is almost always `CLIENT_URL`.

---

## What is not configured here

- **No custom domain.** Both hosts serve their generated URLs.
- **No horizontal scaling.** Presence is in memory, so a second instance would
  not share the roster. Scaling past one instance needs the Socket.IO Redis
  adapter.
- **No CI.** Tests run locally with `npm test` in `server/`; nothing runs them
  on push.
